# Smart Review 痛点分析与需求设计文档

## 1. 为什么需要做这个工具（痛点分析）
- 人工 Code Review 成本高、效率不稳：PR 峰值时容易遗漏风险，质量依赖审查者经验且常受时间压力影响。
- 传统 Lint/静态规则覆盖有限：跨文件语义、上下文关联、风险等级策略难以统一在提交节点前落地。
- 增量变更不透明：团队常对“仅有小改动”掉以轻心，细粒度风险在合并后才暴露，修复成本增大。
- 配置分散且不透明：忽略规则、文件选择逻辑在多工具之间重复维护，成员难以理解“为什么这个文件被跳过/被审查”。
- AI 使用缺乏策略：一刀切启用 AI 成本高、信噪比不稳定，缺少“阻断先于 AI”的质量门槛与并发成本控制。
- 团队对质量与安全基线无感知：提交前缺少统一、明确的校验与反馈，开发者对“该做与不该做”的边界模糊。
- 流程未嵌入开发习惯：未在 `pre-commit` 阶段形成必经的质量门槛，问题常在合并后才暴露。

设计初衷：将提交前校验内嵌到开发流程，提前规避问题；让质量与安全“显性化”，并通过清晰反馈引导开发者改进。

Smart Review 的目标是在提交前引入“策略化且可解释”的审查流程：把静态规则、增量审查与 AI 分析整合为一体，先用规则兜底阻断，再用 AI 在通过规则的变更上给出高质量建议，并以清晰的日志与配置说明增强透明度。

## 2. 目标与价值
- 提前拦截高风险变更：提交时即给出阻断/警告/建议分级结果，降低修复成本。
- 提升团队一致性：风险等级与规则模板统一配置，减少口径差异。
- 降低审查压力：静态规则过滤常见问题，AI 聚焦语义建议，审查者专注关键讨论。
- 增强透明度：每次跳过与审查的原因、来源、命中规则均可解释与追踪。
- 显性化质量与安全要求：把隐性标准工具化并前置到提交节点，形成可执行的门槛。
- 行为引导与教育性反馈：输出可操作建议与示例，在不阻断的场景下提升开发者质量意识。

与普通代码审查的优势对比：
 - 可自定义规则与风险策略：团队可定义标准与分级阻断，规则可迭代与灵活禁用。
 - 可自定义语法/模式匹配：支持精确、通配与正则匹配，适应多语言与多场景需求。
 - 提交前可感知与统一入口：在提交阶段即把关，与持续集成策略一致，减少返工与遗漏。
 - 增量审查与透明度：只关注变更片段，清晰说明命中与跳过原因，降低噪音并提升可解释性。
 - AI 建议与成本控制：规则先行、AI后置，并发与重试可控，稳定输出高价值建议并降低成本风险。



## 3. 用户与使用场景
- 开发者：本地 `pre-commit/pre-push` 或手动执行，查看风险与建议。
- Tech Lead/维护者：在 CI 作为质量门槛使用，强制阻断高风险。
- 安全/合规角色：基于安全规则模板运行，避免敏感信息泄露与危险 API。

主要场景：
- 本地提交前审查暂存区文件（全量/增量）。
- CI 中对变更文件执行统一策略，输出可读报告。
- 指定文件的快速分析与策略验证（调试模式）。

典型用法（CLI）：
- 全量审查暂存区：`node bin/review.js --staged`
- 增量审查（仅变更片段）：`node bin/review.js --staged --diff-only`
- 指定文件：`node bin/review.js --files src/a.js src/b.ts`
- 控制 AI：`node bin/review.js --no-ai` 或 `--ai`

## 4. 需求分析（功能性与非功能性）
### 4.1 功能性需求
- 文件选择与忽略
  - 支持 `ignoreFiles` 多形式：精确匹配（文件名/相对/绝对路径）、glob（`**/*.js`）、正则（`/.../flags` 或普通正则字符串）。
  - 正确处理 Windows 路径分隔符与跨平台兼容。
  - 提供“跳过原因”日志（如：匹配正则、匹配 glob、扩展名不支持）。
- 审查模式
  - 全量审查暂存区文件。
  - Git Diff 增量审查，仅分析新增行或变更片段（lib/utils/git-diff-parser.js）。
- 静态规则引擎
  - 可配置风险等级（阻断/警告/建议），与拦截策略（阻断时跳过 AI）。
  - 规则模板：templates/rules 下可扩展（best-practices、performance、security）。
  - 支持语言注释内指令禁用（如文件局部跳过某规则）。
- AI 智能分析
  - 在无阻断问题时，触发 AI 对变更内容进行语义审查与建议生成。
  - 并发与批量控制（lib/smart-batching.js），降低成本与提升吞吐。
- CLI 与交互
  - `bin/review.js` 提供 `--staged`、`--diff-only`、`--files`、`--ai/--no-ai` 等参数。
  - 清晰的进度、结果输出与失败处理（异常时退出码为 1）。
- 国际化与日志
  - 文案集中管理（lib/utils/i18n.js），便于扩展 en-US/zh-CN。
  - 日志级别：progress/info/debug/error/success。

与实现细节的映射：
- 忽略匹配：`lib/reviewer.js` 的 `matchPattern` 修复了 `**`/`*` 替换冲突（占位符法），并统一路径分隔为 `/`。
- 可审查判定：`isReviewableFile` 综合扩展名、忽略列表与模式匹配，返回状态与原因；`getFileReviewStatus` 用于详细调试输出。
- 增量解析：`lib/utils/git-diff-parser.js` 负责提取新增/变更行与段信息，为静态与 AI 分析提供精确上下文。
- 规则执行：`templates/rules/*` 输出统一问题对象（文件、位置、等级、建议），在 `lib/reviewer.js` 聚合。
- 并发与成本：`lib/smart-batching.js` 对待分析片段分片并发执行；`lib/ai-client-pool.js` 管理客户端与重试策略。
- 国际化与日志：`lib/utils/i18n.js` 管理文案键；`lib/utils/logger.js` 以分级输出进度、原因与结果。

### 4.2 非功能性需求
- 性能：对忽略匹配与注释解析等引入缓存；批处理并发控制避免阻塞。
- 兼容：统一路径分隔符，兼容 Windows 与 POSIX；Node.js >= 16。
- 可扩展：规则模板、国际化目录、外部规则集；配置化风险等级策略。
- 稳定性与安全：错误兜底与退出码管理；日志避免泄露敏感内容；AI 请求最小化。

## 5. 实现思路与设计
### 5.1 忽略规则与匹配逻辑
- 方法：`CodeReviewer.isReviewableFile(filePath)` 与 `getFileReviewStatus(filePath)`。
- 规则顺序：
  1) 精确匹配：文件名、相对路径、绝对路径（路径分隔统一为 `/`）。
  2) 正则：支持 `/.../flags` 与普通正则字符串（含正则特殊字符）。
  3) glob：`*`→`[^/]*`、`?`→`.`、`**`→`.*`（使用占位符避免替换冲突）。
- 常见难点：
  - Windows 路径 `\\` 与 POSIX `/` 的规范化。
  - glob 与正则的边界判断（避免误判与替换污染）。
  - 大型 ignore 列表的性能与缓存命中。
- 日志：在审查入口处输出跳过原因与相对路径，便于理解配置效果。

实现细节：
- `matchPattern` 转换顺序与占位符：先将 `**` 替换为占位符，处理 `*`/`?`，再还原占位符为 `.*`，避免 `**` 被拆解污染。
- 调试输出：命中模式会在 debug 日志中显示转换后的正则（例如 `**/lib/**` → `^.*/lib/.*$`）、匹配的文件与路径来源（相对/规范化）。

### 5.2 增量审查（Git Diff）
- 入口：`reviewStagedDiff()`。
- 流程：解析 staged diff → 静态规则扫描 → 若无阻断则并发触发 AI → 汇总输出。
- 难点：
  - diff 解析的上下文行合并（`contextMergeLines`）。
  - Windows/不同 Git 配置下路径解析稳定性。
  - 控制流早退（例如误用 `return;`）导致结果对象未返回，需通过代码审核与测试规避。

实现细节与修复：
- 在循环中误用 `return;` 会提前返回 `undefined` 并导致 `printResults` 读取 `result.issues` 报错；已改为 `continue;` 保证最终执行 `return this.generateResult()`。
- 结果对象：统一包含 `issues`（本地规则），在无阻断时可能包含 `aiSuggestions`，并附带统计信息（行数、段数）。

### 5.3 静态规则引擎
- 规则来源：`templates/rules` 与外部自定义规则（`useExternalRulesOnly`）。
- 规则输出结构：统一问题对象格式（文件、位置、风险等级、建议）。
- 风险策略：阻断等级问题会阻止 AI 分析，直接返回结果。

实现要点：
- `security.js`、`performance.js`、`best-practices.js` 按语言与场景输出具体模式；支持国际化提示文本。
- 规则禁用：可在代码注释或配置中临时关闭指定规则，提升灵活性。

### 5.4 AI 分析与并发
- AI 客户端管理：`AIClient` 与 `AIClientPool`。
- 并发批处理：`SmartBatching`，依据 `concurrency` 切片处理。
- 难点与要求：
  - 成本控制：仅在必要时启用 AI（`--ai/--no-ai` 与风险策略）。
  - 稳定性：网络重试、错误兜底、超时与取消。

实现要点：
- 仅当静态规则不触发阻断时，才调用 AI；避免“无效建议”浪费成本。
- 批处理把长文件的增量段分片分析，结合并发池提升吞吐并保持稳定。

### 5.5 国际化与日志
- i18n：中文/英文文案目录结构与约定（templates/rules/en-US、zh-CN）。
- 日志：清晰的状态提示、错误报告与审查结果分段输出。

实现要点：
- `lib/utils/i18n.js` 提供统一的键检索与语言切换；规则模板文案与 CLI 输出复用同一套词库。
- `lib/utils/logger.js` 分级输出：progress（进度）、info（信息）、debug（调试）、error（错误）、success（成功），便于在 CI 与本地统一查看。

### 5.6 CLI 交互与退出码
- 正常完成：退出码 0。
- 有阻断或执行错误：退出码 1。
- 输出分为“本地规则审查结果”和“AI审查结果”两段，按文件聚合。

实现要点：
- `bin/review.js` 解析 `--staged`、`--diff-only`、`--files`、`--ai/--no-ai` 等参数，统一入口与报错处理。
- `install.js` 可用于安装钩子或初始化配置（如在项目中创建默认配置）。

## 6. 技术架构概览
- CLI：`bin/review.js`（参数解析、流程控制、结果打印、退出码）。
- 核心：`lib/reviewer.js`（文件选择与忽略、审查模式切换、静态规则执行、AI 分析、结果生成）。
- 并发/批处理：`lib/smart-batching.js`（分片与并发）与 `lib/ai-client-pool.js`（客户端池与重试）。
- 工具：`lib/utils/*`（`git-diff-parser.js`、`logger.js`、`i18n.js`、`concurrency-limiter.js`、`constants.js`、`strip.js`）。
- 配置：`lib/config-loader.js` 与 `lib/default-config.js`（默认值、外部配置加载与合并）。
- 模板：`templates/rules/*`（规则定义与国际化文案）。

数据流概述：
- 输入：CLI 参数 → 选择文件（暂存/指定/增量）→ 忽略匹配与扩展名过滤。
- 处理：静态规则扫描 →（无阻断）AI 分析并发执行。
- 输出：统一结果对象（issues/aiSuggestions/统计）→ 打印与退出码。
